# agent-taskboard Agent 说明书

agent-taskboard 是部门工单记录平台。Agent 可以创建和处理工单、回复、上传附件、查看标签和字典；平台只记录事实，不内置 AI。

支持技能的 Agent 可以把 `{{BASE}}/skills/agent-taskboard/SKILL.md` 装成用户级技能 `agent-taskboard`（接入文案会带上这一步，「我的 → Agent」也常驻一段可复制的安装文字）；技能只负责让你想起本平台，规则仍以本说明书为准。

## 凭证

- 成员 Agent 的 token 由主人通过「我的 → Agent」生成的接入文案交给 Agent，不在工单指令和交接文案中出现。Agent 首次接入时执行接入文案里的两条命令，用 `setx` 把平台地址和凭证存成 Windows 用户环境变量 `TASKBOARD_URL` / `TASKBOARD_TOKEN`；新变量要新开终端才生效，本会话可直接使用。
- 所在平台已经把本平台接口导入为工具时，凭证由平台代管：直接调用工具，不要寻找 `TASKBOARD_TOKEN`；工具返回 401 时停下来告诉主人。成员从接入文案里取出 token，贴进平台的凭证保险箱。
- 后续请求头写 `Authorization: Bearer $TASKBOARD_TOKEN`。读不到这个变量或请求返回 401 时，Agent 要停下来，请主人去「我的 → Agent」生成或换新 token，并重新粘贴接入文案；不要用密码登录，也绝不使用别人的 token。
- 访客是部门级、长期存在的身份；访客链接必须归属一位访客。链接的 `tbg_` 密钥只用于
  认领和凭访问码进入；认领成功返回一次 `tbgd_` 设备凭证和 6 位访问码。已认领后单凭
  链接密钥会被拒绝。换设备时在名下任一链接输入一次访问码，这台设备对这位访客名下
  全部有效链接都可信；之后成员新加的链接也直接可信。浏览器和访客 Agent 共用同一个
  连续输错计数，连续 5 次即锁定这位访客的全部链接，只能请成员重置。
  访客 Agent 后续访问有两种凭证：单工单用
  `Authorization: Bearer tbg_<链接密钥>:<访问码>`；批量处理用
  `Authorization: Bearer tbh_<主页密钥>:<访问码>`。两者都可读取、回复和下载附件；
  若访客尚未认领，先用 `POST /api/v1/guest-links/claim` 或
  `POST /api/v1/guest-home/claim` 带主人的称呼认领。
  访客能访问的工单集合是“名下未撤销、未过期的链接”指向的工单；访问名下没有链接的
  工单会得到 404。认领拿到的链接和访问码必须原样转交主人，不要写进工单、回复、日志或其他系统。
  通过反馈入口代主人提交时，先看请求是否已经带着主人以前拿到的 `tbgd_` 设备凭证：
  带着同一访客的凭证提交，响应会复用 `guest` 并给出稳定的 `home_url` 与新的
  `guest_link.url`，但不再给 `device_token` 和 `access_code`；继续使用原设备凭证与
  原访问码即可。首次提交（或凭证属于已停用访客）会新建 `guest`，响应一次性给出
  `home_url`、`guest_link.url`、`device_token` 和 6 位 `access_code`；这些凭证只能
  原样交给主人，后续入口提交可带上 `device_token` 识别同一位访客。入口的
  `Idempotency-Key` 仍按入口划分，不因带上设备凭证而改变重放范围。
- 工单属于公司商业敏感信息；成员只能看到可见范围内的工单，成员 Agent 按主人的
  可见范围访问；模型的选用遵守公司规定。
- 所有数据接口仍需凭证；本说明书不含任何数据。

## 起手流程

1. 先看工单的 Markdown 视图：`{{BASE}}/api/v1/tickets/<工单编号>?format=markdown`，请求头 `Authorization: Bearer $TASKBOARD_TOKEN`。
2. 照工单末尾「下一步（给 Agent 的操作指引）」执行。
3. 之后的待办看收件箱：`{{BASE}}/api/v1/inbox`。
4. 用变更序号增量轮询：列表接口的 `changed_after=<上次拿到的最大 change>`，只处理之后变化的工单。

## 访客名单与建访客链接

- 主人让你给某张工单建访客链接（或建单时顺带建链接）时，必须先确定链接归属哪位访客：
  读 `GET {{BASE}}/api/v1/guests?q=<名字>` 在部门访客名单里按名字搜索，找到就用
  `guest_id` 选这位已有访客；名单里没有才用 `new_guest_name` 当场新建一位。
  两者都不带会返回 `422 guest_required`，同时带会返回 `422 guest_required`（只能二选一）。
  停用或已并入的访客不能作为目标；前者返回 `409 guest_disabled`，后者返回
  `409 guest_already_merged`，请改选合并后的访客或询问主人是否先恢复。
- 建链接：`POST {{BASE}}/api/v1/tickets/<工单编号>/guest-links`，请求体带
  `{"note": "这条链接的用途", "guest_id": <已有访客id>, "valid_days": 30}`；
  新建访客时把 `guest_id` 换成 `"new_guest_name": "检验科-张三"`。备注只写这条链接的
  用途（如“请补全说明”），人名记在访客上，不要写进备注。建单时顺带建链接则把同样的
  字段放进请求体的 `guest_link` 对象。
- 列表 `GET {{BASE}}/api/v1/tickets/<工单编号>/guest-links` 的每条链接带 `guest_id` 和
  `guest_name`；转发与留痕优先用访客名字。上线前的无主老链接没有这两个字段，仍按备注区分。
- 主人让你把无主老链接归到访客时，调
  `POST {{BASE}}/api/v1/tickets/<工单编号>/guest-links/<链接id>/assign-guest`。
  请求体同样是 `{"guest_id": <已有访客id>}` 或 `{"new_guest_name": "检验科-张三"}` 二选一。
  目标访客未认领而老链接已认领时，老访问码和设备会转给这位访客；目标访客已认领时，
  老链接自己的访问码和设备作废；未认领老链接直接沿用访客状态。操作会写
  `guest_link_assigned` 时间线事件（`reason` 为 `manual`），不发通知；已归属链接返回
  409 `guest_link_already_assigned`，不要尝试重复归属。

## 访客详情与改名

- 主人让你了解某位访客的往来时，用名单里的 `guest_id` 调
  `GET {{BASE}}/api/v1/guests/<guest_id>`。响应的 `tickets` 只列你主人可见范围内的
  工单和这位访客名下指向它们的链接；`guest.disabled_at` 非空表示已停用。
  已并入另一位访客的重复访客不会出现在名单，也不能再被选作建链接的 `guest_id`。
- 主人让你给访客改名时（名字写错或对方换部门），调
  `POST {{BASE}}/api/v1/guests/<guest_id>/rename`，请求体 `{"name": "新名字"}`。
  权限与复制主页文案相同：访客建立者、管理员或名下任一链接的管理人（含其成员 Agent）。
  改名后新回复记新名字，历史署名保持原样；改名本身不写工单时间线。
- **停用和恢复访客不是你能做的**：它们影响多张工单且难撤回，只接受主人在网页上
  亲自操作（`POST /api/v1/guests/<guest_id>/disable|enable`）。成员 Agent 调用会得到
  403 `web_session_required`；收到这个需求时告诉主人去网页的访客管理页操作。
- **合并重复访客也不是你能做的**：它会把 B 的全部链接改归 A、作废 B 的主页、访问码
  和设备，且不能撤回。预览与执行接口
  （`GET /api/v1/guests/<b_id>/merge-into/<a_id>/preview`、
  `POST /api/v1/guests/<b_id>/merge-into`）只接受主人的网页会话；成员 Agent 一律得到
  403 `web_session_required`。收到这个需求时告诉主人去网页的访客管理页先看影响预览，
  再二次确认。

## 访客链接转发文案

- 主人让你把某张工单的访客链接再发给对方时，先读
  `GET {{BASE}}/api/v1/tickets/<工单编号>/guest-links`，找到备注对应的链接并确认
  `share_text_available` 为 true；再 `POST {{BASE}}/api/v1/tickets/<工单编号>/guest-links/<链接id>/share-text`。
- 响应只有 `{share_text}`，里面是**同一条链接**，并按当前标题、有效期和认领状态生成；已认领时会提醒对方换设备要输入当初的访问码。把这段文案原样交给主人或指定的访客，不要改写链接，也不要写入日志、无关工单或其他系统。

## 访客主页与按访客批量处理

- 主人让你把访客主页发给某位访客时，用名单里的 `guest_id` 调
  `POST {{BASE}}/api/v1/guests/<guest_id>/home-share-text`；响应
  `{home_url, share_text}` 可重复复制，其中只有主页地址、没有访问码。只有访客建立者、
  管理员或名下链接管理人会成功；无关成员会得到 403。原样交给主人，不要改写 `home_url`。
- 拿到访客主页和访问码后，先从 `/h/<主页密钥>` 取出 `tbh_` 后面的密钥，用
  `Authorization: Bearer tbh_<主页密钥>:<访问码>` 调
  `GET {{BASE}}/api/v1/guest-home`。响应的 `tickets` 是这位访客名下所有仍有效链接
  对应的工单；轮到访客的排在前面，`waiting_on_you=true`，`reason` 写原因；
  `read_only=true` 表示已关闭，只能读不能回复。
- 批量处理推荐顺序：先保存整份 `tickets` 列表；逐张按 `api` 读取；对每张分别回复或
  修订说明，正文不要串单；每张的回复都要自报 `author_name` 并如实写「由 Agent 写成」。
  只打开主页不会写入访问记录，逐张读取才会按访客名字记录。
- 主页和链接凭证共用同一个访问码错误计数：连续 5 次输错会锁定这位访客的全部工单。
  收到 401 `access_code_invalid` 时先停下核对；收到 403 `access_code_locked` 时告诉主人
  需要成员重置，不要继续尝试。
- `409 share_text_unavailable` 表示这是上线前的老链接，平台没有可恢复的密钥；告诉主人需要换一个新地址，不要伪造旧文案。已撤销或已过期会返回 `409 link_not_extendable`。
- `rotate-key` 一般只在 `share_text_available` 为 false 时使用（老链接或服务端加密密钥丢失）；链接疑似外泄时也可以用来换地址。无论哪种情况，都要先向主人说明后果并取得确认。
  主人明确确认要换新地址后，再带 `Idempotency-Key` 调用
  `POST {{BASE}}/api/v1/tickets/<工单编号>/guest-links/<链接id>/rotate-key`。
  重置链接**只换这一条链接的地址**：访问码、已认领设备、备注和认领状态都不变，
  对方名下其他工单与主页也不受影响；旧地址立即失效，把新文案发给对方即可。
- 响应 `{url, share_text, reset_text}` 是同一条链接的新地址、常规转发文案和重置文案；
  重置链接不再连带重置访问码，因此没有 `access_code`。把 `reset_text` 原样交给主人或
  指定的访客，不要改写链接。重试复用同一个 `Idempotency-Key`，会返回首次结果，
  不会再次换地址。
- 重置访问码（访客级）与重置主页地址只接受成员本人的网页会话，成员 Agent 调用会得到
  403 `web_session_required`。主人提出这类需求时，请转告其在网页的工单详情「重置访问」
  向导里操作；访问码重置会作废该访客名下全部设备并生成只显示一次的新码，主页地址重置
  只换主页地址。无主老链接的链接级重置访问码（`…/guest-links/<链接id>/reset-access-code`）
  成员 Agent 仍可代为调用；对有主链接调用会返回 409 `guest_access_code_guest_level`，
  应改用上面说的访客级入口。

## 先给主人审核再提交

- 模式：主人可以把你设为「可直接发」或「必须走草稿」，新签发的 token 默认可直接发。用 `GET {{BASE}}/api/v1/session` 查看自己的模式：`viewer.agent.draft_mode` 为 `direct` 或 `required`。可直接发时走下面的本地预览，必须走草稿时走平台草稿。
- 要审核的动作：建单、回复（包括交付）、修订说明。打标签、指派、协作者、关闭或重开都直接生效。
- 建单和建单草稿都可以带 `collaborators`（成员 id 或姓名的数组，日常说的「抄送」）：
  建单时这些人会一并加入协作者、收到「加入协作」通知；只能选在职成员，
  指派人和创建者本人不需要写进去。

### 本地预览（可直接发）

1. 写好后，把要提交的内容写成主人本机上的一份 Markdown 文件：`~/.taskboard/previews/<工单编号或 new>-<动作>.md`（Windows 是 `%USERPROFILE%\.taskboard\previews\`），动作用 `create`、`reply`、`deliver`、`brief`。文件开头用 YAML front matter 写元信息：工单编号、动作、模板和字段、指派、抄送、附件的本地绝对路径；正文就是要提交的原文。
2. 把这个文件的**绝对路径**单独占一行告诉主人，再用一两句话说明对谁、做什么、要点是什么。不要在聊天里贴全文。你不能写本地文件时例外：把同样格式的完整预览贴在聊天里。
3. 主人提出修改意见，你就改文件，再报一次绝对路径。主人也可能直接改这个文件，所以每次改之前都先重读，不要覆盖主人的改动。
4. 只有主人明确说「提交」「发」之后才提交：
   - 重读文件，按文件里的内容原样提交，不要再自己润色；
   - 先读工单时间线，看从你写稿时读到的最后一个序号 `[seq]` 之后有没有新事件，有的话把新内容告诉主人，暂不提交；
   - 附件到这时才上传；
   - 回复和修订说明带上 `confirm_through_seq`（你读到的最后一个序号）。返回 `409 ticket_changed` 时，说明工单又有了新变化，把 `new_events` 的内容告诉主人，等主人再确认；
   - 成功后报工单链接，并删除这份预览文件。
5. 只有主人在当次任务里明确说「不用给我看，直接发」，才可以跳过预览，而且只对这一次任务有效。
6. 署名为「主人 的 Agent · 你的名字」，不带「经主人确认」。

### 平台草稿（必须走草稿）

- 202 不等于已发出：照常调用原接口，平台会存成草稿，返回 `202`，带 `draft`、`preview_url` 和 `next`。保存时就按原接口校验，有错当场返回。存成草稿后，工单上看不到这份内容，对方也收不到通知。照 `next` 把 `preview_url` 交给主人。上传附件不走草稿，会直接生效。
- 修改：先 `GET {{BASE}}/api/v1/drafts/{id}`，再用 `PUT` 整体替换，带上 `base_version`。遇到 `409 draft_version_conflict` 就重新读，在最新版上改，不要覆盖主人的改动。pending 的模板建单草稿响应另带只读的计算字段 `rendered_brief_md`（按发出时同一路径渲染的说明预览）和 `template_fields`（字段定义），`PUT` 时忽略它们，要改内容就改 `request.fields`。
- 不能发出或丢弃：这两个操作返回 `403 web_session_required`。要放弃一份草稿，请主人在网页上丢弃。想确认结果，就 GET 这份草稿：`status: "sent"` 时会带 `result`；返回 404 说明可能已被丢弃。
- 署名与存档：发出后署名「主人 的 Agent · 你的名字 · 经主人确认」；主人改过其中任意一版时，写「经主人修改并确认」；有多个 Agent 执笔时，署最后一个执笔的。草稿的每一版都会随正式内容存档，可见范围内的成员都能看到，访客看不到，所以不要在草稿里写不该让这些成员看到的话。

### 两种模式都适用

- `409 draft_pending`：只要你这一方在这张工单上有一份待确认的平台草稿，回复和修订说明都会被挡住。不论草稿是哪个 Agent 写的、还是主人自己写的，也不论你是哪种模式。处理方法：在那份草稿上 PUT，或者请主人在网页上发出或丢弃。另外，工单已关闭时写回复会返回 `409 ticket_closed`，请主人先重开。
- 访客 Agent 不受这些限制。

## 怎么选模板

先看各模板的适用场景，再用一个判断问题收窄：发起人自己想不想定怎么做？已经想清楚交付物和做法的用分配任务；只清楚问题、输入和想要的效果，做法交给接收人的用提需求；只想要答案的用问题咨询；东西坏了的用 Bug 反馈。提需求不要求发起人写怎么做，分配任务要求发起人写清交付物和做法。模板列表和详情都会返回 `scenario` 字段。拿不准时用回复问发起人，不要替发起人猜。

## 等待方与收件箱

等待方表示当前轮到谁行动，由最后一条回复或访客修订说明推导，不能手动设置。访客还没补全说明时轮到访客，这张工单不会进入成员收件箱。收件箱是某位成员「现在轮到我」的开启工单清单；同一成员的所有成员 Agent 共用这份收件箱。看到自己一方在等待方中，或工单进入收件箱，就该继续处理。

向主人汇报收件箱时不要只报编号或截断标题。每张待办都按「编号 + 完整标题 +
谁做了什么 + 最后回复时间」列出：完整标题不得缩写或省略，用 `trigger.name` 加
`reason` 写「谁做了什么」；`last_reply_at` 为 null 时用 `created_at` 写「创建于 …」。

主人被抄送（协作者）的工单不在收件箱里。主人说「看看抄送我的单」时，用
`{{BASE}}/api/v1/tickets?collaborator=me&status=open`；要看已关闭的协作工单，把
`status` 换成 `closed`。协作者能看、能回复，但不进入轮次：你的回复不会改变等待方，
也不能代创建者验收。

成员 Agent 向访客追问时也要先给主人审核；信息已经完整的单不要随手回复——成员 Agent 的回复算主人一方行动，会把等待方切换成访客。

## 可见范围与敏感信息

- 工单属于公司商业敏感信息。成员只能看到自己创建、当前被指派、被加入协作，以及未指派时由自己初筛的工单；管理员可以看到全部。成员 Agent 的可见范围与其主人相同，列表、搜索、计数、收件箱和读写都只限于这些工单。
- 访问不到的工单会返回 404，与编号不存在无法区分；不要反复尝试或猜测编号。标签、维度和别名字典是全员共享的，不代表某张工单可见。
- 已归档并从服务器移除的可见工单会返回 `410 ticket_archived`，错误对象的 `archived_ticket`
  带编号、标题、归档时间、操作人和归档包名。要如实告诉主人“这张工单已归档出平台，
  需要管理员导入归档包才能查看”；不要把墓碑信息当作仍可执行的工单内容。
- 访客访问必须使用访客链接凭证；不要把工单内容、访客链接或访问码写入无关工单、通知或其他系统。

## 请求注意事项

- 所有写请求都带 `Idempotency-Key: <每次业务操作固定的随机值>`，重试不会重复建单或重复回复。
- Windows 下请求体必须是 UTF-8。把 JSON 写入文件后用 `curl --data-binary @body.json` 发送；PowerShell 用 `[Text.Encoding]::UTF8.GetBytes(...)` 作为 `-Body`。
- 附件先 `POST {{BASE}}/api/v1/tickets/<工单编号>/attachments` 上传（multipart 字段名 `file`），再用返回的 `att_N` 引用：图片嵌正文，普通文件写 `[名字](att:att_N)`；不属于某个字段的文件放进回复或说明修订的 `attachment_ids`，说明里的日志等整单文件不要拼进字段。
- 要查看已有附件时，先 `GET {{BASE}}/api/v1/attachment-links/<att_N>` 取短时链接，再下载：

  ```
  ATTACHMENT_URL=<attachment-links 响应里的 url>
  curl -L "$ATTACHMENT_URL" -o "<filename>"
  ```

  下载会跳转，必须带 `-L`；签名地址几分钟后失效，不能存下来复用。链接只给自己用，
  不要转贴到工单或聊天里；`curl -L` 跨主机跳转时不会带上 Authorization。
- 读取接口里附件带 `slim_removed_at` / `slim_package_name` 时表示它已被瘦身移出服务器：不要尝试下载（会得到 410 `attachment_slimmed`）；需要这个文件时请人联系管理员，用瘦身包恢复。
