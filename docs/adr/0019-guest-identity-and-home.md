# ADR 0019：访客成为长期身份，一个访问码通行名下全部工单，并有访客主页

## 状态

已接受（2026-11-09 讨论定稿）。取代 ADR 0015；改写 ADR 0012 的风险论证。

## 背景

原来访客只是“凭某条访客链接参与某一张工单的人”，每条链接各自认领、各自有访问码。同一个人要填好几张单时，要记好几条链接和好几个访问码；过几天回来看进展，分不清哪条链接对应哪张单。成员给同一个人反复建单的情况越来越多，这个问题也越来越明显。

## 决策

- **访客**变成部门级、长期存在的身份，由成员建立和命名。新建访客链接时必须选已有访客或当场新建一位；上线前建的老链接可以无主，成员可以事后把它归到某位访客。
- 每位访客有一个**访客主页**：长期有效的带凭证地址，列出其名下链接仍有效的工单，轮到访客的排在前面。
- **访问码升到访客级**：一位访客只有一个访问码，凭主页或名下任一链接认领一次，这台设备对其全部链接都可信。权限、有效期、撤销仍然挂在单条链接上。
- 重置操作拆成三种：**重置链接**只换单条链接的地址；**重置访问码**以访客为单位，作废其全部设备；**重置主页地址**单独进行。重置文案改成“主页地址加新访问码”。
- 老链接归到访客时：访客还没认领的，链接原有的认领、访问码和设备直接转给访客；访客已经认领的，链接原有的访问码和设备作废，改用访客的。
- 反馈入口提交时，设备已被某位访客认领的，就以这位访客的身份提交；否则新建一位访客。重复的访客由成员合并。

## Considered Options

- **按设备自动聚合**（浏览器记住认领过的链接，列成“本机的工单”）：不需要新身份，安全边界也不变。但换设备就看不到了，访问码仍然一条链接一个，第一次收到时还是要处理 N 条链接。
- **访客自己归并**（在一条链接里输入另一条链接的访问码，把两条并到一起）：不需要成员参与。但要访客学新操作，而且仍然先要记住多个访问码。
- **给访客开轻量账号**：和“访客无需登录”的定位冲突，还要另做账号管理。
- **访客主页存在，但访问码仍然一条链接一个**：只解决了“找链接”，没解决“记访问码”。

## Consequences

- **爆炸半径变大**：ADR 0012 当初接受“数据库连同密钥一起泄露”的理由是“一条访客链接只能访问一张工单”，这条理由现在不成立了。一位访客的主页地址加访问码一旦泄露，会暴露其名下全部有效工单。我们接受这个风险，靠以下措施缓解：认领后独占、访问码只显示一次并且连续输错 5 次锁定、可以随时重置访问码和主页地址、可以停用访客。主页只列链接仍有效的工单。
- ADR 0015 把“重置链接”和“重置访问码”绑在一起的两条理由，在新模型下都改由别的途径解决：访客找不到链接时看主页；访问码丢了或疑似外泄时，在访客层面重置访问码。所以本 ADR 取代 0015。
- 访客是部门共享的，但成员查看某位访客时，只能看到自己可见范围内的工单，访客聚合不能用来绕过工单的可见范围。
- 访客的 Agent 凭主页地址加访问码就能处理该访客的全部工单，说明书要相应补充。
- 成员 Agent 建访客链接时可以选已有访客或新建访客；合并访客、停用访客、重置访问码影响多张工单且难撤回，只开放给成员在网页上操作。
- 访客停用等同于其名下链接全部撤销，轮次沿用“链接撤销后未填写回到指派人”的现有规则，不新增规则。
