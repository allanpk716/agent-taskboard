# 成员 Agent 照常调用原接口，平台存成草稿返回 202，只有成员本人能在网页上发出

成员 Agent 写的建单、回复（含交付）和说明修订原来会立刻对外可见，成员没有机会先看一眼。我们没有给 Agent 另开一套「写草稿」的接口，而是让 Agent 照常调用原接口：这个 Agent 设为「必须走草稿」时，平台按原接口完整校验后不产生正式内容，存成一份只有成员本人看得到的草稿，返回 `202` 和 `preview_url`。发出和丢弃只接受网页会话，Agent 调用返回 `403 web_session_required`。草稿模式按每个成员 Agent 单独设置，默认必须走草稿；上线时已有的 token 一律改为必须走草稿，并在网页上提示一次。

## Considered Options

- **给 Agent 另开草稿接口，由 Agent 决定写草稿还是直接发**：成员把不住关，Agent 忘了或者判断错了，内容照样直接对外；Agent 说明书也要讲两套写法。
- **Agent 可以自己发出草稿**：把关就形同虚设，ADR 0003 署名里的「经某成员确认」也就不可信了。
- **草稿作为工单的一种状态（待审核、预发布）**：工单的其他参与者会从时间线、未读、等待方里察觉到它，而草稿在发出前不应对工单产生任何影响；建单草稿还会占用工单编号，丢弃后编号出现空洞。
- **默认可直接发，由成员逐个开启**：多数成员不会主动去改设置，新功能等于没上线；所以默认必须走草稿，需要的成员再改回可直接发。

## Consequences

- 不认识 `202` 的 Agent 会误以为已经发出，所以响应里带 `next`，工单指令和 Agent 说明书也写明「202 不等于已发出，把 `preview_url` 交给成员」。
- 每位成员在每张工单上只有一个草稿位，回复和说明修订共用，成员本人和名下所有 Agent 算同一方；有草稿期间这一方直接回复或修订都返回 `409 draft_pending`，即使是可直接发的 Agent。
- 草稿写成后工单可能又有了新变化，发出时要带 `confirm_through_seq`，不够新就返回 `409 ticket_changed`，由成员看过后再决定是否发出。
- 草稿的每一版都随正式内容存档为起草过程，工单可见范围内的成员都能看到，访客看不到；丢弃的草稿物理删除，不留档。
- 访客 Agent 不受草稿限制。
