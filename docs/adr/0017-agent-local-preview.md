# ADR 0017：可直接发的成员 Agent 先在本地预览，主人确认后再提交；默认改为可直接发

## 状态

已接受（2026-11-05 讨论定稿）。修订 ADR 0008 中的默认模式。

## 背景

ADR 0008 让成员 Agent 照常调用原接口，平台存成草稿，主人在网页上发出。用了一段时间，大家觉得太麻烦：每次都要从 Agent 切到网页去找草稿；想改的话，要在网页上复制修改指令再贴回给 Agent。大多数时候主人本来就坐在 Agent 旁边，没必要绕一趟网页。

## 决策

成员 Agent 设为**可直接发**时，在本地预览、主人确认后提交，规则写进说明书，平台不参与：

- 建单、回复（含交付）、修订说明写好后，Agent 把要提交的内容写成主人本机上的一份 Markdown 文件，放在 `~/.taskboard/previews/<编号或 new>-<动作>.md`（Windows 是 `%USERPROFILE%\.taskboard\previews\`）。文件开头用 front matter 写元信息（工单、动作、模板、字段、抄送、附件的本地绝对路径等），正文就是要提交的原文。
- Agent 把这个文件的**绝对路径**单独占一行告诉主人，再附一两句摘要，不在聊天里贴全文，免得出现两份内容。不能写本地文件的 Agent 例外，把完整预览贴在聊天里。
- 主人提出修改意见，Agent 改文件后重新报路径；主人也可以直接改这个文件。只有主人明确说「提交」「发」之后，Agent 才提交：先重读文件，按文件原样提交，主人改过的地方不能覆盖；提交前确认工单在这期间有没有新变化，有的话先把新内容告诉主人，暂不提交；附件到这时才上传；提交成功后报工单链接，并删除预览文件。
- 只有主人在当次任务里明确说「不用给我看，直接发」，Agent 才可以跳过预览，而且只对这一次任务有效。无人值守的 Agent 应该设为「必须走草稿」。

平台侧的改动：

- 回复和修订说明接口新增可选参数 `confirm_through_seq`，语义和发出草稿时相同：工单在这个序号之后有新的可见事件，就返回 `409 ticket_changed`，带上 `new_events` 和 `through_seq`。用来兜住 Agent 漏查的情况。建单没有序号，不需要这个参数。
- 新签发的 token 默认可直接发。上线时已有的 token 一律改为可直接发，并在网页上提示一次。想继续用平台草稿的成员自己改回「必须走草稿」。迁移时已经存在的草稿不动。
- 直接提交的内容署名「主人 的 Agent · 名字」，不加「经主人确认」。平台核实不了主人是否在本地看过，这个标注只留给从平台草稿发出的内容。
- 工单指令不再写「内容会先存成草稿」，改成「按说明书，先给主人审核再提交」，由 token 的模式决定实际走哪条路。

平台草稿原样保留，包括 `draft_pending`、起草过程存档、`web_session_required` 等规则，适合主人不在 Agent 旁边的场景。

## Considered Options

- **下线平台草稿**：起草过程存档、草稿列表、修改指令都要拆掉，而无人值守的场景仍然需要平台把关。
- **由 Agent 每次自己决定走草稿还是本地预览**：等于让 Agent 自己决定要不要把关，这正是 ADR 0008 否决过的方案。
- **Agent 声明「已经主人确认」，平台据此署名**：平台无法核实，「经主人确认」就不可信了。
- **只靠说明书约束「提交前先查工单有没有变化」**：Agent 会漏查；参数只需复用现成的 `confirm_through_seq`，代价很小。
- **只改新 token 的默认值**：已有用户正是觉得草稿麻烦的那批人，还要一个个去改设置。

## Consequences

- 直接提交的内容不再有「经主人确认」，读者看到的署名与 ADR 0003 的普通成员 Agent 署名相同。
- 预览文件在主人本机，平台看不到，也不存档；没有起草过程。
- 说明书的「草稿」一节分成「本地预览（可直接发）」和「平台草稿（必须走草稿）」两部分。
