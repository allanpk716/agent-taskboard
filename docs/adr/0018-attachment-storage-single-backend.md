# ADR 0018：附件存储全局单后端、离线迁移，库内记录实际后端

## 状态

已接受（#314）。

## 背景

附件存储要支持阿里云 OSS，本地仍是默认后端，并且必须能在本地和 OSS 之间双向迁移、随时切回。
有两种做法：一是每个附件在附件表里记录自己所在的后端，可以边运行边迁移；二是全局只有一个
后端，迁移时停机。

## 决策

采用全局单后端。`[attachments] backend = "local" | "oss"` 决定所有附件放在哪里，任何时刻
库里的附件要么全在本地，要么全在 OSS。迁移由专门的命令在停服状态下完成：逐个复制，校验
大小和 CRC，然后切换。回切就是反向执行同一条命令。

数据库设置表里记录附件实际所在的后端（`attachments_backend`，OSS 时还记 bucket 和 prefix），
这条记录只由迁移命令改写；唯一的例外是恢复备份：恢复后把标记改写为当前配置的后端，并把
附件补齐到该后端。服务启动时把它和配置比对，不一致就拒绝启动，并提示应该运行哪条
迁移命令。这样可以防止只改了配置而没有迁移数据。

不按附件记录后端的原因：部门规模下附件量是 GB 级，同地域内网传到 OSS 不占 1M 出口带宽，
也不收流量费，停机迁移只要几分钟。在线迁移的收益很小，代价却很大：统计、备份镜像、归档
打包、恢复、清理都得处理「一部分在本地、一部分在 OSS」的混合状态，而且两个后端要同时可用。

## 后果

- 每个调用方只面对一个存储接口实现，没有混合状态的分支。
- 迁移需要停机窗口；以后附件量涨到停机迁移不可接受时，需要重新考虑按附件记录后端。
- 对象 key 和本地相对路径一一对应（`<prefix>attachments/<id>`），迁移不需要映射表。`<prefix>` 是本系统在桶里的根前缀（默认 `agent-taskboard/`），备份和归档包也放在它下面（`backups/`、`archive-packages/`），因为同一个桶会放多个系统的数据。
