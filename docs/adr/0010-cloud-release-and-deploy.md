# ADR 0010：云端发布与部署：合并版本号、镜像冒烟门禁、一条命令部署并自动回滚

日期：2026-10-23

## 状态

已接受。部分取代 [ADR 0002](0002-stack-deploy-and-self-update.md)（前后端独立版本、UpdateHub 发布服务端）和 [ADR 0009](0009-cloud-docker-deployment.md)（回滚只换镜像 tag）。

## 背景

迁到云服务器后的第一个版本（0.12.0）暴露出几个问题。一是镜像里的后端取不到 `index.html`，网页全部 404，流水线只检查了 health，没有发现（#239）。二是部署靠手工敲命令：备份、改 compose、拉镜像、核对版本，步骤多，也容易漏。三是回滚只换回旧镜像 tag，但数据库迁移只能前进，新版本跑过迁移以后，旧二进制不一定能打开这份库。另外，前后端分两个 tag 发布，可镜像里前后端本来就一起构建、一起上线，分开的版本号只给兼容检查添了负担。

## 决策

- **生产只保留云端 Docker 形态。** Windows/NSSM 原地更新不再是生产路径，文档和流水线不再为它维护。
- **前后端合并为一个版本号，只打 `server/vX.Y.Z`。** 一次发布同时构建后端、前端和镜像，`release-web` 流水线停用。前端 manifest 里的 `min_server` 兼容检查随之简化。桌面客户端仍单独打 `client/vX.Y.Z`，见 [ADR 0011](0011-desktop-client-standalone-distribution.md)。
- **CI 镜像冒烟门禁。** 镜像构建完成后，先在构建机上启动容器，检查首页、一条前端路由、静态资源，以及 health 返回的 `server_version` 和 `web_version` 是否等于本次版本。全部通过后，才推送版本 tag 和 `:latest`。
- **镜像推送 GHCR，阿里云 ACR 作为可选的第二个仓库。** 服务器目前直接从 GHCR 拉取。流水线已支持同时推送 ACR 个人版：配置好 Secrets 就会推送，未配置时跳过。ACR 暂缓开通，等 GHCR 拉取确实不稳定时再启用：选和服务器同一个地域，服务器经 VPC 内网地址拉取。
- **一条命令部署，失败自动回滚。** 仓库里放部署脚本 `deploy/cloud/deploy.sh <版本>`，每次从对应的 tag 上传到服务器的部署目录后执行。脚本依次执行：在运行中的容器里做升级前备份，拉取新镜像，把 compose 的镜像 tag 改成新版本并重启，最后经公网地址核对版本号和首页。任何一步失败，都切回旧 tag，并恢复升级前的备份。服务器上的 `config.toml` 和数据卷由脚本外维护，脚本不改动它们。
- **compose 写死版本号，不用 `:latest`。** 线上跑的是哪个版本，看 compose 文件就知道。回滚目标就是改动前写在里面的那个 tag。
- **宿主机 Caddy 整站反代到后端。** 站点块模板写进 `docs/deploy-and-release.md`，模板里不出现真实服务器信息。#239 修好之前，Caddy 临时直接托管前端文件。
- **端口只由 `config.toml` 决定。** compose 里不起作用的 `TASKBOARD_PORT` 环境变量删除。

## Considered Options

- **继续同时维护 NSSM 原地更新**：两套部署形态各自要测、要写文档，原地更新器的回滚、exe 替换这些逻辑在容器里也用不上。生产只有一处，维护一套就够。
- **立即开通 ACR**：服务器在国内，从 GHCR 拉取可能慢或失败；但拉取失败时部署脚本还没动线上，重试即可，眼下不值得多维护一个仓库。
- **回滚只换回旧镜像**：新版本如果已经跑过迁移，旧二进制可能读不了新表结构。必须连同升级前的备份一起恢复。
- **compose 用 `:latest`**：看不出线上是哪个版本，回滚时也不知道该切回哪个 tag。
- **前后端继续独立版本**：镜像总是同时带前后端，独立版本号既不能单独上线，又要维护一张兼容矩阵。

## Consequences

- 发布 = 合并 → 打 `server/vX.Y.Z` tag → CI 冒烟并推送镜像 → 执行部署脚本 → 经公网核对。CI 冒烟失败时镜像不会推送，部署脚本也就拉不到新版本。
- 自动回滚会恢复升级前的备份，升级开始到回滚完成这段时间里新写入的数据会丢掉。这段时间只有几分钟，部署时平台照常可用，这个代价可以接受。
- 管理页的在线更新按钮在容器部署下仍然只提示升级镜像。原地更新器中服务于 NSSM 的部分以后可以清理，本决策不要求立即删除。
- 启用 ACR 时，在 GitHub Secrets 里配置 ACR 的登录凭据，再把服务器 `deploy.env` 的 `IMAGE_REPO` 改成 ACR 地址，代码不用改。
