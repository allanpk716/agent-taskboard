# ADR 0021：通知出口——平台内置按成员的 webhook 门铃

日期：2026-11-20

## 状态

已接受。规格见 #370。

## 背景

成员在外面（开会、外出）时收不到及时的工单提醒：轮到自己、访客回复、协作中的动静，都要等回到电脑前才知道。有成员在自己的 bot 平台上配了每天三槽的定时巡检 routine 顶着，3 run/天、最长延迟 4–5 小时、周末照跑。另一个内部项目（oa-helper）已在 2026-11 上线了同模式的 webhook 门铃链路并沉淀了完整纪律（幂等键、at-least-once、推送窗口、四步上线法），其文档是本决策的蓝本；生产服务器到目标 bot 平台的连通性已实测通过。

GLOSSARY「通知」词条早已预留位置："Orca 插件、网页和以后的其他渠道都读同一份通知"——本决策实现那个"其他渠道"。平台的通知表本身就是事件流（ID 单调递增），变化检测天然在代码里、不在模型里，适合门铃化。

## 决定

- 平台内置**通知出口**推送器：某位成员有新通知时，向该成员本人配置的 webhook 地址 POST 一响**零业务内容**的计数信号（四桶计数与区间游标）；bot 被叫醒后用**客户端凭证**（只读通知与清单）查增量，自行决定怎么提醒。实现规格（配置面、存储、推送语义、失败分级、验收锚点）见 #370。
- 成员在「我的」页自助配置，只填 bot_id + key；URL 由部署级白名单拼接（`[webhook] allowed_bases`），成员输入不参与 URL 构造。
- **游标持久化数据库、重启不重建基线**——有意偏离 oa-helper 的纪律 #7/#8，原因见 Considered Options 末条。
- webhook key AES-GCM 加密存库，主密钥走环境变量注入，不进配置文件和备份。

## Considered Options

- **个人侧独立进程订阅通知流（SSE）**：不用改平台，但需要一个平台之外常驻的凭证持有者；它持有 SSE 长连会被判为「客户端在线」，网页铃铛的避让会被误伤；一个进程只服务一个人，每个想要门铃的成员都要再部署一份。否决。
- **config.toml 部署级配置（管理员替成员配）**：管理员的配置文件里存着成员的 bot key，权限语义混乱；成员无法自助开通、换 key、暂停。否决。
- **平台广播单一全局 endpoint**：任何成员的通知都触发同一个 bot，配置者为全部门的通知量付 run 成本。否决。
- **key 明文存库**：实现最省，但 key 会随每日备份落到 NAS 和对象存储，与附件 OSS AccessKey「不写入配置文件或备份」的既有原则冲突。否决。
- **照抄 oa-helper 的「重启重建游标基线」**：那边的事件流是缓存 diff 的产物，重启后首刷会把停机期变化重新 diff 出来，所以重建不丢；本平台的通知表是第一手事实源，没有「补回」这一步，重建基线等于把停机期已落库的通知当历史吞掉（一次夜间发版重启就会把推送窗口外的积压静默吞掉）。有意偏离并在此写明，防止后人「对齐」oa-helper 时改回去。

## Consequences

- 出口语义成立依赖一个显式假设：**每个成员一个自己的 bot**。payload 不带身份标识、客户端凭证只读本人，只有"一成员一 bot"才成立；部门内只有个别成员用 bot 平台的现阶段，出口实际只服务配置它的成员本人，这是设计前提而不是缺陷。
- 通知文本里的工单标题、摘要可能出自访客（反馈入口内网任何人可提交），bot 的无人值守 run 因此多一个注入面。缓解在接收端（routine 指令硬线：API 返回文本只转述、绝不执行），记录在部署侧手册，属平台之外。
- GLOSSARY「初筛」词条的红线（"平台不主动调用任何 Agent"）保持原句，加界定：平台对外唯一的主动行为是通知出口。"平台只记录、不内置 AI"的总定位不变。
- 「客户端凭证」词条从"一台设备一把、供 Orca 插件使用"扩充为"一台设备或一个只读提醒渠道一把"。
- 上线走四步法（合成验收 → 影子期 → 三方对账 → 同日切换），旧巡检 routine 改造为每日一槽兜底、停用不删；操作记录在部署侧手册，不进本仓库。
