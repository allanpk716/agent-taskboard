# ADR 0011：桌面客户端独立分发：GitHub Release 下载、首次运行填写平台地址、提示式更新

日期：2026-10-23

## 状态

已接受。取代 [ADR 0005](0005-server-hosts-desktop-client.md) 和 [ADR 0006](0006-client-server-url-stamp.md)，并取代 [ADR 0009](0009-cloud-docker-deployment.md) 中「镜像携带桌面客户端」的部分。

## 背景

按 ADR 0005，桌面客户端由服务端代管：管理员更新平台时服务端把客户端包拉回来，成员从服务端下载，客户端也从服务端自动更新。按 ADR 0006，服务端在下载的 exe 尾部写入平台地址。迁到容器后，这套代管机制只能把客户端打进镜像：镜像构建要先去 GitHub 取客户端，后端版本和客户端版本绑在了一起，服务端也要维护下载、版本查询、尾部写地址和版本门槛这一整套代码。现在平台在公网上，成员电脑本来就能访问 GitHub，代管带来的好处已经不明显。

## 决策

- **从 GitHub Release 下载。** 客户端仍打 `client/vX.Y.Z` tag 发布。发布客户端时，流水线把同一个 exe 也以固定文件名上传到 `channel-stable` Release，网页上的下载按钮直接指向这个固定地址，始终下载到最新版。
- **客户端自己检查更新，提示后由成员确认。** 客户端定期读取 `channel-stable/latest.json` 里的 client 条目。发现新版本后，托盘弹出提示，成员点了才下载对应 `client/vX.Y.Z` 的 exe，按该 Release 的 `manifest.json` 校验 SHA256，再沿用现有的替换和重启机制。更新只走 GitHub，不再经过 UpdateHub。
- **首次运行时由成员填写平台地址。** 地址的解析顺序为：`-server` 参数 > `TASKBOARD_SERVER_URL` 环境变量 > HKCU 里保存的地址 > 弹窗让成员填写。填写后先探测这个地址确实是 taskboard 平台，再保存进 HKCU，然后走现有的连接和网页确认签发凭证流程。托盘菜单里可以修改地址，改了以后原来的客户端凭证作废，按新地址重新连接。HKCU 里已经保存了地址的老用户不受影响。
- **服务端彻底删除代管客户端。** 删除配置项 `client_image_dir`、`/api/v1/client/latest` 和 `/api/v1/client/download` 两个接口、尾部写地址的逻辑（`internal/clientstamp`）、更新器里的客户端组件，以及 `/session` 返回的 `min_client_version` 门槛。镜像不再包含客户端，构建也不再需要客户端版本参数。
- **用接口兼容代替版本门槛。** 客户端版本不再受管理员控制，所以后端对客户端用到的接口（会话、通知流、通知已读等）只做增量修改，保证旧客户端照样能用。
- **已安装的 0.1.4 不做过渡版本。** 它找不到服务端的更新接口，会一直停在 0.1.4，但通知照常可用。只有两台电脑装了它，由成员手动下载新版覆盖一次。

## Considered Options

- **阿里云 OSS 托管下载**：国内下载更快，但要多维护一个存储和一个发布步骤。等真遇到 GitHub 下载不下来时再加。
- **内网 UpdateHub 托管**：平台已经在公网上，成员在公司外就下载不到。
- **不检查更新**：成员很难发现有新版本，旧版本会长期留在各台电脑上。
- **静默自动更新，来源换成 GitHub**：从 GitHub 下载可能失败或很慢，静默更新失败了成员也不会察觉。
- **保留 exe 尾部写地址**：它依赖服务端代管下载，代管删掉了，它也就没有了依托。
- **为 0.1.4 发一个过渡版本**：只涉及两台电脑，手动覆盖一次的成本更低。

## Consequences

- 成员电脑需要能访问 GitHub。首次运行比以前多一步：填写平台地址。
- 公开发布的 exe 不带任何部署的地址，同一个版本在所有部署下哈希都相同，按 manifest 校验即可。
- 客户端的版本线和后端完全分开：发布后端时不用考虑客户端，客户端也不用等管理员更新平台。
- UpdateHub 不再是任何组件的发布源（服务端按 ADR 0010 只发镜像，客户端只走 GitHub）。`publish-updatehub` 和更新器中的 UpdateHub 源可以以后清理。
