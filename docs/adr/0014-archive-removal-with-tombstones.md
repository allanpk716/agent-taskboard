# ADR 0014：工单可完整归档出平台并留下墓碑

## 状态

已接受（#226/#236/#237）。

## 背景

平台原设计把「工单不能删除」作为审计边界：附件与时间线长期累积，备份目录里还有一份
附件镜像，服务器空间只增不减。只归档附件不足以离线阅读完整工单；直接彻底删除又会
让旧链接变成不可解释的 404，并破坏历史通知的语义。

## 决策

归档是唯一能让工单离开平台的方式。管理员先生成包含结构化数据、可读 Markdown 和附件
的完整 zip 包，下载保存后必须显式确认，才能从服务器移除工单。移除在一个数据库事务内
删除全部关联数据并写入墓碑；提交后删除附件主文件、备份附件镜像和暂存包。

墓碑保留内部序号、工单编号、标题、关闭时间、归档时间、操作人和归档包名称。详情、
网页、访客旧链接和成员 Agent 读取命中墓碑时返回明确的 `ticket_archived` 与墓碑信息；
通知条目保留。编号分配把墓碑计入，永不复用。

归档包必须完整包含结构化数据与附件，而不是只导出附件：离线阅读需要说明、回复、
时间线、起草过程和访问记录，完整恢复也需要这些数据。管理员可以上传已保存的归档包；
平台先校验 manifest 和全部文件哈希，再按墓碑匹配情况逐张选择导入。引用缺失或仍在
平台上的工单只拒绝该张，选中的其他工单按原 ID、原编号恢复并删除墓碑。

## 后果

- 旧链接不再是无法区分的 404，而能说明工单去了哪里。
- 工单数据从当前库移除，附件目录与备份镜像的空间可以真正释放；旧数据库备份中的
  工单会随备份轮换自然过期。
- 归档包成为完整恢复工单的唯一来源，安全等级与数据库备份相同，必须离线妥善保存。
- 导入只允许恢复处于墓碑状态的工单，避免重复；恢复后的工单仍是已关闭状态，可以照常
  重新开启或再次归档。
