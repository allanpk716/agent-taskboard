成员 Agent 之间的工单交接

要回答的问题（工单「成员 Agent 之间的工单交接」）：我用自己的 Agent 建一张工单、指派给同事；同事的 Agent 自己发现这张工单，只凭读到的内容就知道要做什么、做完怎么交回；我的 Agent 再得知交付并验收。现有协议补上哪些东西，这条链路才能跑通？

在「Agent 访问协议原型」的基础上新增了四样东西：轮到谁（把“等待方”扩展到成员之间）、收件箱 GET /api/inbox、回复上的交付标记 deliver，以及 Markdown 版末尾的操作指引。API token 一律代表某个具名的成员 Agent（ADR 0003）。

用法：先看「引导场景」，逐个点按钮。页面下方有三个人的收件箱和每张工单的“轮到谁”，每点一步都会刷新，刚发生的变化以黄色标出。平台是浏览器内存中的模拟，刷新即重置。

拿来讨论的设计选择

  1. 轮到谁（扩展“等待方”）：工单上的“等待方”从“本部门 / 对方”扩展为具体的一方：指派人、发起人（任务的创建者）或访客，仍然只由最后一条回复推导，不能手动设置。规则：
    · 尚无回复、或最后是访客回复 → 轮到指派人；
    · 任务的创建者和指派人是两位不同成员时：指派人一方回复 → 轮到发起人；发起人一方回复 → 轮到指派人；第三位成员的回复不改变轮次；
    · 其他情况（反馈，或自己派给自己）：成员回复 → 轮到访客，与原规则一致。
    成员 Agent 的回复算作它所属成员那一方。
  2. 收件箱 GET /api/inbox：列出“现在轮到我”的开启工单，并给出原因（新指派给你 / 已交付待你验收 / 对方提问 / 退回修改 / 访客回复了），以及从哪个事件序号开始读新内容。收件箱属于成员：同一成员名下的每个 Agent 看到的是同一份。Agent 定时调用它即可，不需要人口头转告。
  3. 交付：回复可以带 deliver: true，表示“做完了，请验收”。只有指派人一方能交付。交付不会关闭工单，由发起人验收：通过就以“完成”关闭；不通过就普通回复写明问题，工单自动退回指派人。不新增任何状态。
  4. 操作指引：?format=markdown 的末尾按“你是谁、现在轮到谁”生成一段“下一步”，写明要调用的 HTTP 请求和请求体。拿到工单地址的 Agent 不需要 CLI、MCP 或额外文档，照着做就行。JSON 版对应地给出 viewer.role 和 viewer.your_turn。
  5. 创建并指派：POST /api/tickets {template, title, fields, labels, assignee}。指派人只能是成员，填成成员 Agent 会被拒绝（成员 Agent 不能被指派）。响应附带一句 share_text，成员可以直接转发给同事，告知对方“有活给你”。
  6. 改派：POST …/assign {assignee}，记入时间线。改派后，原指派人的回复不再影响轮次，工单出现在新指派人的收件箱里，原指派人的收件箱里则不再有它。
  7. 验收可以由人来做：发起人的 Agent 看到“已交付”后，可以先问发起人本人，再由 Agent 关闭，或者本人在网页上关闭。平台不区分这两种做法，时间线上的署名会如实记录是谁关闭的。
