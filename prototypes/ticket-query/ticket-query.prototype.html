工单查询接口：外部 Agent 按条件列出工单

要回答的问题（工单「工单查询接口：外部 Agent 按条件列出工单」）：初筛、查重、统计这几类外部 Agent 怎样按条件列出工单、只拿变化过的工单、按维度计数，又怎样按俗称找到标准标签？

在「成员 Agent 之间的工单交接」原型的基础上新增：列表 GET /api/tickets、计数 GET /api/tickets/counts、带别名的标签字典 GET /api/labels 与 GET /api/labels/resolve、别名维护 POST /api/labels/aliases，以及打标签 POST …/labels。

用法：先看「引导场景」，逐个点按钮。页面下方是几条常驻查询（初筛队列、未指派、轮到访客）的实时结果，以及每张工单的内部状态，每点一步都会刷新，刚发生的变化以黄色标出。平台是浏览器内存中的模拟，刷新即重置。

拿来讨论的设计选择

  1. 列表 GET /api/tickets，仅限成员。条件之间是“并且”：
    · status=open|closed|all，默认 open；kind=task|report；template=；
    · label= 必须带有、no_label= 必须不带有，都可以重复；值可以写 维度:值、不带维度的标签（如 待初筛），或 维度:*（这个维度有/没有任何值）。值可以写别名，平台换成标准值后在 filters 里回显；字典里找不到时返回 422 unknown_label_value 并给出近似值；
    · assignee= 成员名、me 或 none（未指派）；creator= 成员名、me 或 guest（经反馈入口提交）；waiting_on=assignee|creator|guest|department|me；
    · 时间范围：created_after/before、updated_after/before、closed_after/before，写日期或日期时间；
    · q= 关键词，在标题、说明和回复里找，每项带回 matched_in 和片段 snippet（查重用）。
  2. 分页与排序：sort=-updated（默认）、updated、-created、created、-closed、change；limit 默认 50，最大 200；响应给出 total 和 next（下一页的完整地址，没有下一页时为 null）。
  3. 返回粒度：每项是摘要：编号、标题、类型、状态、关闭原因、创建者、指派人、标签、模板、waiting_on（与单工单 GET 的格式相同）、创建/更新/关闭时间、回复数，以及 read_full（Markdown 全文地址）。include=brief 时再带上说明（Markdown 和按字段的 fields）。时间线不在列表里给，要看就读单张工单。format=markdown 返回一张表，供 Agent 直接阅读。
  4. 增量拉取：平台有一个全局递增的变更序号，工单的任何事件（回复、标签、指派、关闭等）都会把它推进。列表响应总是带上当前的 cursor；Agent 下次用 changed_after=<cursor> 就只拿到这之后变化过的工单（可以和其他条件一起用，自动按变更顺序排）。不用时间戳，避免时钟和同一秒内多次变更的问题。
  5. 统计：GET /api/tickets/counts?group_by=…，筛选条件与列表完全相同。group_by 可以是一个标签维度、status、kind、assignee、close_reason 或 waiting_on。只做计数：一张工单在同一维度有多个值时，每个值各算一次，所以各组之和可能大于 total；没有这个维度的计入 (无)。首次响应时长、处理时长等指标仍由 Agent 从列表和时间线推导，平台不预先计算。
  6. 标签字典与别名：GET /api/labels 列出每个维度的值，每个值附带 aliases，另列出不带维度的标签。GET /api/labels/resolve?q=7600 按标准值、别名或近似匹配返回候选，并注明是怎么匹配上的（exact / alias / fuzzy）。成员可以用 POST /api/labels/aliases {label, alias} 加别名；一个别名只能指向一个标准值，冲突时返回 409。打标签时写别名也会换成标准值。
  7. 与已有接口一致：错误统一为 {error:{code,message,hint}}；访客调用这些接口返回 403 members_only；waiting_on、编号和地址的格式与单工单 GET 相同。GET /api/inbox 仍然保留：它就是“轮到我”的查询，另外附带原因和增量地址。每个新接口各对应一条 CLI 子命令和一个 MCP tool（见每次请求的对照）。
