Agent 访问协议原型

要回答的问题（工单「Agent 访问协议原型」）：Agent 拿到工单地址或访客链接后，怎么读工单（JSON 和 Markdown 各长什么样）、怎么回复、怎么上传附件或写外部文件引用、怎么打标签？

页面里的平台是浏览器内存中的模拟服务，刷新即重置。成员和访客调用的是同一套 HTTP API，区别只在于凭证：成员用账号 token，访客直接把访客链接里的密钥当 token 用。每个请求旁边都列出它将来对应的 CLI 子命令和 MCP tool。

用法：先看下方「引导场景」，逐个点按钮；也可以在「自由操作」里任选身份，修改请求后发送。最底部是平台的完整内部状态（成员视角），刚发生的变化会以黄色标出。

拿来讨论的设计选择

      
    
        
  1. 访客链接即凭证：链接格式为 /g/<密钥>，密钥直接作为 Authorization: Bearer 使用，不再另外“换”一个 token。撤销和过期即时生效。链接里不出现工单编号，访客先调 /api/session 查出它指向哪张工单。
    2. 
        
  2. 一次读全：GET /api/tickets/{编号或序号} 一次返回说明、附件和完整时间线；加 ?format=markdown 返回一份适合 Agent 直接阅读的 Markdown；轮询时用 /timeline?after=N 增量拉取。
    3. 
        
  3. 能力表 viewer.can：每次读取都会告诉 Agent 当前能做什么（回复、上传、编辑说明、打标签、关闭……），Agent 不需要自己推断权限。
    4. 
        
  4. 附件分两步：先上传，拿到 att: 引用；再在回复或说明中引用（正文里的 ![](att:…) 或 attachment_ids）。待用附件也计入 200MB 配额，24 小时未被引用即清除。CLI 的 tb reply --file 会把这两步合成一步。
    5. 
        
  5. 超限的处理：单个文件超过 50MB 或整张工单超过 200MB 时返回 413，hint 提示改用 NAS 路径。外部文件引用只是正文里的文本，不需要专门的接口。
    6. 
        
  6. 标签字典：维度下不存在的值默认拒绝，并给出近似写法的建议；传 allow_new: true 才会新建。新维度只能由管理员添加。不带维度的标签可以随手打。
    7. 
        
  7. 说明的并发编辑：用 base_revision 做乐观锁，版本不一致时返回 409，Agent 需要重新读取、合并后再提交。
    8. 
        
  8. 统一的错误格式 {error:{code,message,hint}}：hint 告诉 Agent 下一步可以怎么做。访客访问其他工单时返回 404 而不是 403，避免泄露其他工单是否存在。
    9. 
        
  9. 访客视角的时间线有空号：标签事件对访客隐藏，所以访客看到的事件序号会跳号。可以接受，还是要给访客单独编号？
